11 <a id="l2" href="#l2">2</a> name: regression-bisect
12 <a id="l3" href="#l3">3</a> description: Find the exact commit that introduced a regression using git bisect. Use when something used to work and now does not, when a test that previously passed now fails, when a performance or memory regression appeared between releases, or when the user says &quot;this broke&quot;, &quot;worked last week&quot;, or &quot;which commit caused this&quot;. Prefer this over reading diffs or reasoning about likely causes.

15 <a id="l6" href="#l6">6</a> # Regression bisect
16 <a id="l7" href="#l7">7</a> 
17 <a id="l8" href="#l8">8</a> Do not reason about which commit &quot;probably&quot; caused a regression. Bisect finds it
18 <a id="l9" href="#l9">9</a> in log2(n) steps with certainty. A 1000-commit range resolves in ~10 builds.
19 <a id="l10" href="#l10">10</a> 
20 <a id="l11" href="#l11">11</a> ## Step 1: Build a reproducer that exits with a status code
21 <a id="l12" href="#l12">12</a> 
22 <a id="l13" href="#l13">13</a> This is the whole job. Everything else is mechanical.
23 <a id="l14" href="#l14">14</a> 
24 <a id="l15" href="#l15">15</a> The reproducer must exit **0 when the code is good** and **non-zero when bad**.
25 <a id="l16" href="#l16">16</a> Make it as fast and as narrow as possible — it will run once per bisect step.
26 <a id="l17" href="#l17">17</a> 
27 <a id="l18" href="#l18">18</a> ```bash
28 <a id="l19" href="#l19">19</a> #!/usr/bin/env bash
29 <a id="l20" href="#l20">20</a> # /tmp/bisect-test.sh
30 <a id="l21" href="#l21">21</a> set -euo pipefail
31 <a id="l22" href="#l22">22</a> 
32 <a id="l23" href="#l23">23</a> # Build. If the build itself fails, this commit cannot be judged: exit 125.
33 <a id="l24" href="#l24">24</a> make -j&quot;$(nproc)&quot; &gt;/dev/null 2&gt;&amp;1 || exit 125
34 <a id="l25" href="#l25">25</a> 
35 <a id="l26" href="#l26">26</a> # The actual check. Narrow it to the single failing case.
36 <a id="l27" href="#l27">27</a> pytest tests/test_parser.py::test_nested_arrays -q
37 <a id="l28" href="#l28">28</a> ```
38 <a id="l29" href="#l29">29</a> 
39 <a id="l30" href="#l30">30</a> Exit code contract for `git bisect run`:
40 <a id="l31" href="#l31">31</a> 
41 <a id="l32" href="#l32">32</a> | Code | Meaning |
42 <a id="l33" href="#l33">33</a> |---|---|
43 <a id="l34" href="#l34">34</a> | 0 | good |
44 <a id="l35" href="#l35">35</a> | 1–124, 126, 127 | bad |
45 <a id="l36" href="#l36">36</a> | 125 | untestable, skip this commit |
46 <a id="l37" href="#l37">37</a> | 128+ | abort the bisect |
47 <a id="l38" href="#l38">38</a> 
48 <a id="l39" href="#l39">39</a> **Store the script outside the repository** (`/tmp`, or a path in
49 <a id="l40" href="#l40">40</a> `.git/info/exclude`). Bisect checks out old trees; a script inside the worktree
50 <a id="l41" href="#l41">41</a> will be overwritten or deleted mid-run.
51 <a id="l42" href="#l42">42</a> 
52 <a id="l43" href="#l43">43</a> `chmod +x` it. Verify it manually on a known-bad commit (expect non-zero) and a
53 <a id="l44" href="#l44">44</a> known-good one (expect zero) before starting. A miscalibrated script silently
54 <a id="l45" href="#l45">45</a> produces a confident wrong answer.
55 <a id="l46" href="#l46">46</a> 
56 <a id="l47" href="#l47">47</a> ## Step 2: Establish the bounds
57 <a id="l48" href="#l48">48</a> 
58 <a id="l49" href="#l49">49</a> ```bash
59 <a id="l50" href="#l50">50</a> git status                      # must be clean; stash or commit first
60 <a id="l51" href="#l51">51</a> git bisect start
61 <a id="l52" href="#l52">52</a> git bisect bad                  # current HEAD is broken
62 <a id="l53" href="#l53">53</a> git bisect good v1.4.0          # last known-good tag or commit
63 <a id="l54" href="#l54">54</a> ```
64 <a id="l55" href="#l55">55</a> 
65 <a id="l56" href="#l56">56</a> If no known-good point is known, walk backwards until the reproducer passes:
66 <a id="l57" href="#l57">57</a> 
67 <a id="l58" href="#l58">58</a> ```bash
68 <a id="l59" href="#l59">59</a> git checkout HEAD~50 &amp;&amp; /tmp/bisect-test.sh; echo &quot;exit=$?&quot;
69 <a id="l60" href="#l60">60</a> ```
70 <a id="l61" href="#l61">61</a> 
71 <a id="l62" href="#l62">62</a> Double the step each time until it passes, then use that as the good bound.
72 <a id="l63" href="#l63">63</a> 
73 <a id="l64" href="#l64">64</a> ## Step 3: Run it
74 <a id="l65" href="#l65">65</a> 
75 <a id="l66" href="#l66">66</a> ```bash
76 <a id="l67" href="#l67">67</a> git bisect run /tmp/bisect-test.sh
77 <a id="l68" href="#l68">68</a> ```
78 <a id="l69" href="#l69">69</a> 
79 <a id="l70" href="#l70">70</a> Report the `&lt;sha&gt; is the first bad commit` output verbatim, plus
80 <a id="l71" href="#l71">71</a> `git show --stat &lt;sha&gt;`.
81 <a id="l72" href="#l72">72</a> 
82 <a id="l73" href="#l73">73</a> Then, always:
83 <a id="l74" href="#l74">74</a> 
84 <a id="l75" href="#l75">75</a> ```bash
85 <a id="l76" href="#l76">76</a> git bisect reset
86 <a id="l77" href="#l77">77</a> ```
87 <a id="l78" href="#l78">78</a> 
88 <a id="l79" href="#l79">79</a> Leaving a repository in a bisecting state is a trap for the next session.
89 <a id="l80" href="#l80">80</a> 
90 <a id="l81" href="#l81">81</a> ## Variants
91 <a id="l82" href="#l82">82</a> 
92 <a id="l83" href="#l83">83</a> **Performance regression** — bisect on a threshold, not on pass/fail:
93 <a id="l84" href="#l84">84</a> 
94 <a id="l85" href="#l85">85</a> ```bash
95 <a id="l86" href="#l86">86</a> ns=$(hyperfine --style none --export-json /dev/stdout ./bench \
96 <a id="l87" href="#l87">87</a>      | jq &#x27;.results[0].mean&#x27;)
97 <a id="l88" href="#l88">88</a> awk -v t=&quot;$ns&quot; &#x27;BEGIN { exit (t &gt; 0.250) ? 1 : 0 }&#x27;
98 <a id="l89" href="#l89">89</a> ```
99 <a id="l90" href="#l90">90</a> 
100 <a id="l91" href="#l91">91</a> Pick the threshold to sit clearly between the known-good and known-bad
101 <a id="l92" href="#l92">92</a> measurements, not at the midpoint of noise. Run the benchmark on both bounds
102 <a id="l93" href="#l93">93</a> first to see the spread.
103 <a id="l94" href="#l94">94</a> 
104 <a id="l95" href="#l95">95</a> **Flaky failure** — the reproducer must loop, or bisect will mark good commits
105 <a id="l96" href="#l96">96</a> bad and give a wrong answer:
106 <a id="l97" href="#l97">97</a> 
107 <a id="l98" href="#l98">98</a> ```bash
108 <a id="l99" href="#l99">99</a> for i in $(seq 1 30); do ./run-test || exit 1; done
109 <a id="l100" href="#l100">100</a> ```
110 <a id="l101" href="#l101">101</a> 
111 <a id="l102" href="#l102">102</a> If the failure rate is below ~10%, raise the iteration count until a known-bad
112 <a id="l103" href="#l103">103</a> commit fails reliably. If it cannot be made reliable, bisect is the wrong tool —
113 <a id="l104" href="#l104">104</a> use `dynamic-analysis` (TSan for races, ASan for use-after-free) instead.
114 <a id="l105" href="#l105">105</a> 
115 <a id="l106" href="#l106">106</a> **Noisy history** — skip merge commits or vendored-code churn:
116 <a id="l107" href="#l107">107</a> 
117 <a id="l108" href="#l108">108</a> ```bash
118 <a id="l109" href="#l109">109</a> git bisect start --first-parent    # follow mainline only
119 <a id="l110" href="#l110">110</a> git bisect skip $(git rev-list --merges good..bad)
120 <a id="l111" href="#l111">111</a> ```
121 <a id="l112" href="#l112">112</a> 
122 <a id="l113" href="#l113">113</a> **Bug is in a dependency, not your code** — bisect the dependency&#x27;s repo with
123 <a id="l114" href="#l114">114</a> your reproducer pinned against it, or bisect your lockfile history.
124 <a id="l115" href="#l115">115</a> 
125 <a id="l116" href="#l116">116</a> ## After the culprit is found
126 <a id="l117" href="#l117">117</a> 
127 <a id="l118" href="#l118">118</a> 1. Read the diff. Explain the mechanism — *why* that change causes this
128 <a id="l119" href="#l119">119</a>    failure. If the mechanism is not clear, the bisect result may be a
129 <a id="l120" href="#l120">120</a>    coincidence of a flaky reproducer; re-verify by checking out the parent
130 <a id="l121" href="#l121">121</a>    commit and confirming it passes.
131 <a id="l122" href="#l122">122</a> 2. Write a regression test that fails on the bad commit and passes on its
132 <a id="l123" href="#l123">123</a>    parent. Show both runs.
133 <a id="l124" href="#l124">124</a> 3. Then fix it.
134 <a id="l125" href="#l125">125</a> 
135 <a id="l126" href="#l126">126</a> Do not revert without understanding the mechanism. The bad commit may have been
136 <a id="l127" href="#l127">127</a> fixing something else.</pre>
