10 <p>rules/ponytail.md (1870 bytes)</p><pre class="src"><a id="l1" href="#l1">1</a> ## Ponytail: lazy senior dev mode
11 <a id="l2" href="#l2">2</a> 
12 <a id="l3" href="#l3">3</a> Source: https://github.com/DietrichGebert/ponytail (`.agents/rules/ponytail.md`).
13 <a id="l4" href="#l4">4</a> Lazy means efficient, not careless. The best code is the code never written.
14 <a id="l5" href="#l5">5</a> 
15 <a id="l6" href="#l6">6</a> Before you write code, stop at the first rung that holds:
16 <a id="l7" href="#l7">7</a> 
17 <a id="l8" href="#l8">8</a> 1. Does this need to be built at all? (YAGNI)
18 <a id="l9" href="#l9">9</a> 2. Does it already exist in this codebase? Reuse the helper, util, or pattern.
19 <a id="l10" href="#l10">10</a> 3. Does the standard library already do this? Use it.
20 <a id="l11" href="#l11">11</a> 4. Does a native platform feature cover it? Use it.
21 <a id="l12" href="#l12">12</a> 5. Does an already-installed dependency solve it? Use it.
22 <a id="l13" href="#l13">13</a> 6. Can this be one line? Make it one line.
23 <a id="l14" href="#l14">14</a> 7. Only then: write the minimum code that works.
24 <a id="l15" href="#l15">15</a> 
25 <a id="l16" href="#l16">16</a> Climb the ladder after you understand the problem, not instead of it. Read the
26 <a id="l17" href="#l17">17</a> task and the code it touches. Trace the real flow end to end.
27 <a id="l18" href="#l18">18</a> 
28 <a id="l19" href="#l19">19</a> Bug fix = root cause, not symptom. Find every caller of the function you touch.
29 <a id="l20" href="#l20">20</a> Fix the shared function once. One guard there is a smaller diff than one guard
30 <a id="l21" href="#l21">21</a> for each caller.
31 <a id="l22" href="#l22">22</a> 
32 <a id="l23" href="#l23">23</a> - No abstractions that were not explicitly requested.
33 <a id="l24" href="#l24">24</a> - No new dependency if you can avoid it.
34 <a id="l25" href="#l25">25</a> - No boilerplate that nobody asked for.
35 <a id="l26" href="#l26">26</a> - Deletion over addition. Boring over clever. Fewest files possible.
36 <a id="l27" href="#l27">27</a> - Shortest working diff wins, but only after you understand the problem.
37 <a id="l28" href="#l28">28</a> - Question complex requests: &quot;Do you need X, or does Y cover it?&quot;
38 <a id="l29" href="#l29">29</a> - If two stdlib approaches are the same size, pick the edge-case-correct one.
39 <a id="l30" href="#l30">30</a> - Mark a deliberate simplification that has a known ceiling (global lock,
40 <a id="l31" href="#l31">31</a>   O(n²) scan, naive heuristic) with a `ponytail:` comment. Name the ceiling and
41 <a id="l32" href="#l32">32</a>   the upgrade path.
42 <a id="l33" href="#l33">33</a> 
43 <a id="l34" href="#l34">34</a> Not lazy about: understanding the problem, input validation at trust
44 <a id="l35" href="#l35">35</a> boundaries, error handling that prevents data loss, security, accessibility,
45 <a id="l36" href="#l36">36</a> calibration for real hardware, and anything explicitly requested.
46 <a id="l37" href="#l37">37</a> 
47 <a id="l38" href="#l38">38</a> Ponytail does not replace &quot;Definition of done&quot; or &quot;Test strategy&quot;. If they
48 <a id="l39" href="#l39">39</a> conflict, those sections win.</pre>
