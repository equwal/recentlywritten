10 <p>rules/patches.md (2472 bytes)</p><pre class="src"><a id="l1" href="#l1">1</a> ## MANDATORY: Show changes as readable diffs; give unapplied patches as a runnable command
11 <a id="l2" href="#l2">2</a> 
12 <a id="l3" href="#l3">3</a> Two cases. Never give loose code lines or whole files.
13 <a id="l4" href="#l4">4</a> 
14 <a id="l5" href="#l5">5</a> **Change you already made (applied).** Show the diff inline, in a fenced block tagged `diff`, so the user reads it with color and no command. Do not make him run a command (`git show`, `diff -u`, `cat`) just to see a change.
15 <a id="l6" href="#l6">6</a> 
16 <a id="l7" href="#l7">7</a> **Change the user must apply** (you could not apply it: denied, blocked, needs his hands or another host). Give one fenced block tagged `bash` (the desktop app adds a Run button only to `bash` blocks) that applies it. The Run button types into his Terminal panel, which runs PowerShell, so a bash heredoc fails there. For another host, pipe a here-string script to ssh (see &quot;One message, one click&quot;); inside it, `cd DIR &amp;&amp; patch -p1 &lt;&lt;&#x27;PATCH&#x27;` ... `PATCH`. Use an absolute `DIR` and the correct `-p` level. The patch text inside is the diff, so he can read it before he runs it.
17 <a id="l8" href="#l8">8</a> 
18 <a id="l9" href="#l9">9</a> - Make diffs with `diff -u` or `git diff`, with context lines and `@@` headers with line numbers. Check an unapplied patch with `patch --dry-run` before you show it.
19 <a id="l10" href="#l10">10</a> - Long diffs: show the relevant hunks inline and say how many lines/files you left out.
20 <a id="l11" href="#l11">11</a> - Give a whole file only when the file is new or the user asks for the whole file.
21 <a id="l12" href="#l12">12</a> - When you edit files yourself, use your edit tools as usual; this rule is about what you show the user.
22 <a id="l13" href="#l13">13</a> 
23 <a id="l14" href="#l14">14</a> **One message, one click.** The user prefers one large runnable block over several small commands. Put every step he must run (all patches, installs, checks, the commit) in a single `bash`-tagged block, so the desktop app&#x27;s Run button does it all in one click. Never split it into blocks he has to copy or run one by one.
24 <a id="l15" href="#l15">15</a> 
25 <a id="l16" href="#l16">16</a> - His Terminal panel can be Windows PowerShell 5.1. It strips `&quot;` inside native-program arguments, prefixes piped text with a BOM, and ends lines with CRLF. A copied block can also lose its tabs.
26 <a id="l17" href="#l17">17</a> - For a remote host, send the script on stdin: a `@&#x27;` ... `&#x27;@` here-string piped to `ssh HOST &#x27;awk &#x27;&#x27;{gsub(/[^ -~\t]/,x)}1&#x27;&#x27; | sh&#x27;`. Keep `&quot;` out of the ssh argument. Start the script with `set -e`.
27 <a id="l18" href="#l18">18</a> - Never rely on a literal tab in the block. Make one with `t=$(printf &#x27;\t&#x27;)`, or append Makefile recipes with `printf &#x27;\t...&#x27;`. Prefer `sed` line edits guarded by a `sha256sum -c` of the file over patches whose context holds tabs or trailing spaces.
28 <a id="l19" href="#l19">19</a> - Before you give the block, run it with a dry-run switch in both `powershell.exe -File` and `pwsh -File`.</pre>
