11 <a id="l2" href="#l2">2</a> 
12 <a id="l3" href="#l3">3</a> Formerly AssistKey. The package id, the repository and the code keep the old name.
13 <a id="l4" href="#l4">4</a> 
14 <a id="l5" href="#l5">5</a> Remaps the hardware keys of an Android device - volume keys, the Power button,
15 <a id="l6" href="#l6">6</a> and whatever else the device has - to arbitrary actions, with multi-tap,
16 <a id="l7" href="#l7">7</a> press-and-hold and key combinations. Also: navigation in any mix of button bar,
17 <a id="l8" href="#l8">8</a> gestures and the Power key; a frontlight level below the system&#x27;s floor; and a
18 <a id="l9" href="#l9">9</a> recent-apps list made for e-ink.
19 <a id="l10" href="#l10">10</a> 
20 <a id="l11" href="#l11">11</a> It runs on any Android 12+ device. The **Viwoods AiPaper Reader** is the first
21 <a id="l12" href="#l12">12</a> device profile, because that is where it was built; see *Device profiles*.
22 <a id="l13" href="#l13">13</a> 
23 <a id="l14" href="#l14">14</a> Open source under [GPL-3.0-or-later](LICENSE). Three builds:
24 <a id="l15" href="#l15">15</a> 
25 <a id="l16" href="#l16">16</a> - `play`: on Google Play, as a free download with a one-time licence. Publishing,
26 <a id="l17" href="#l17">17</a>   products, pricing and how the beta is run and ended are in
27 <a id="l18" href="#l18">18</a>   [play/CHECKLIST.md](play/CHECKLIST.md).
28 <a id="l19" href="#l19">19</a> - `full`: the APK for direct install. It carries the apps of other makers and
29 <a id="l20" href="#l20">20</a>   adds shell access through Shizuku.
30 <a id="l21" href="#l21">21</a> - `fdroid`: on F-Droid. Free and complete, with no licence check. See
31 <a id="l22" href="#l22">22</a>   [fdroid/](fdroid/).
32 <a id="l23" href="#l23">23</a> 
33 <a id="l24" href="#l24">24</a> The app holds no `INTERNET` permission.

46 <a id="l37" href="#l37">37</a> ## Set up a button
47 <a id="l38" href="#l38">38</a> 
48 <a id="l39" href="#l39">39</a> The main screen is a drawing of the device. Each button shows what it does
49 <a id="l40" href="#l40">40</a> now. Tap a button, or two buttons for a combination. Choose how you press it.

59 <a id="l50" href="#l50">50</a> ## Two builds
60 <a id="l51" href="#l51">51</a> 
61 <a id="l52" href="#l52">52</a> One app, one id, one signature, two flavours:
62 <a id="l53" href="#l53">53</a> 
63 <a id="l54" href="#l54">54</a> | Flavour | For | Shizuku |
64 <a id="l55" href="#l55">55</a> |---|---|---|
65 <a id="l56" href="#l56">56</a> | `play` | Google Play. `./gradlew bundlePlayRelease` | No code, no permission |
66 <a id="l57" href="#l57">57</a> | `full` | Direct install. `./gradlew assembleFullRelease` | Yes |
67 <a id="l58" href="#l58">58</a> 
68 <a id="l59" href="#l59">59</a> Shizuku is on Google Play and so are apps that use it, so Play does not forbid
69 <a id="l60" href="#l60">60</a> it. The `play` flavour leaves it out anyway: an app that holds an accessibility
70 <a id="l61" href="#l61">61</a> service and a shell has a harder review, and the store build must be the safe
71 <a id="l62" href="#l62">62</a> one. `shell/Shell.kt` exists once per flavour with the same surface; the `play`
72 <a id="l63" href="#l63">63</a> one always answers &quot;not available&quot;, and every feature falls back by itself.
73 <a id="l64" href="#l64">64</a> `Shell.SUPPORTED` hides the rows that would lead nowhere.

75 <a id="l66" href="#l66">66</a> ## Shell access
76 <a id="l67" href="#l67">67</a> 
77 <a id="l68" href="#l68">68</a> *`full` flavour only.*
78 <a id="l69" href="#l69">69</a> 
79 <a id="l70" href="#l70">70</a> Android keeps several things from every installed app: the Power key, the
80 <a id="l71" href="#l71">71</a> navigation bar, system gestures, a maker&#x27;s own key settings, the backlight
81 <a id="l72" href="#l72">72</a> node. The shell user can reach them. [Shizuku](https://shizuku.rikka.app/)
82 <a id="l73" href="#l73">73</a> (MIT API, free app) gives the app that user from the device itself, through
83 <a id="l74" href="#l74">74</a> wireless debugging - no computer, no root. *Setup &gt; Shell access* walks through
84 <a id="l75" href="#l75">75</a> it. Everything that depends on it degrades honestly without it.
85 <a id="l76" href="#l76">76</a> 
86 <a id="l77" href="#l77">77</a> | With shell access | Without |
87 <a id="l78" href="#l78">78</a> |---|---|
88 <a id="l79" href="#l79">79</a> | Power: any taps, hold, true combinations, read from `/dev/input` | Hold (assistant role) and double press (default camera) only |
89 <a id="l80" href="#l80">80</a> | Bar and gestures switched in-app | The adb commands are shown |
90 <a id="l81" href="#l81">81</a> | Recent apps: the real task list, apps can be closed | Rebuilt from the usage log |
91 <a id="l82" href="#l82">82</a> | Extra-dim light (needs root-level shell) | Not available |
92 <a id="l83" href="#l83">83</a> 
93 <a id="l84" href="#l84">84</a> Implementation notes that cost time:
94 <a id="l85" href="#l85">85</a> 
95 <a id="l86" href="#l86">86</a> - Shizuku&#x27;s bound *user service* cannot be used: its starter dies inside
96 <a id="l87" href="#l87">87</a>   `LoadedApk.makeApplication` on Android 16 before our class loads. `Shell`
97 <a id="l88" href="#l88">88</a>   uses Shizuku&#x27;s remote-process call, and the key watcher is a pipe from
98 <a id="l89" href="#l89">89</a>   `getevent -q &lt;node&gt;` on the nodes that declare the key.
99 <a id="l90" href="#l90">90</a> - While Power is managed, `power_button_short_press`, `power_button_long_press`
100 <a id="l91" href="#l91">91</a>   and the double-tap camera gesture are set to nothing; the firmware values are
101 <a id="l92" href="#l92">92</a>   saved first and restored whenever shell access, the licence, the bindings or
102 <a id="l93" href="#l93">93</a>   the service stop justifying it. Restoring needs no shell: the app grants
103 <a id="l94" href="#l94">94</a>   itself `WRITE_SECURE_SETTINGS` through the shell on first contact. The press
104 <a id="l95" href="#l95">95</a>   that wakes the screen is never a gesture; Power + Volume up stays the power
105 <a id="l96" href="#l96">96</a>   menu.

107 <a id="l98" href="#l98">98</a> ## Device profiles
108 <a id="l99" href="#l99">99</a> 
109 <a id="l100" href="#l100">100</a> `device/Device.kt`. A profile adds only what a maker did differently: extra
110 <a id="l101" href="#l101">101</a> keys, its own key settings, a gesture switch, a brightness floor. Unknown
111 <a id="l102" href="#l102">102</a> devices get the generic profile plus any supported key the key filter has
112 <a id="l103" href="#l103">103</a> actually seen (a page-turn button appears the first time it is pressed).
113 <a id="l104" href="#l104">104</a> 
114 <a id="l105" href="#l105">105</a> New profiles come from **device reports** (*Advanced &gt; Device report*): model,
115 <a id="l106" href="#l106">106</a> firmware, input devices and the keys they declare, navigation overlays, a
116 <a id="l107" href="#l107">107</a> whitelist of key and navigation settings, the light&#x27;s range. The user sees
117 <a id="l108" href="#l108">108</a> every line and sends it themselves by email or share sheet. There is no
118 <a id="l109" href="#l109">109</a> automatic telemetry, because there is no `INTERNET` permission; adding one is a
119 <a id="l110" href="#l110">110</a> deliberate product decision, not a code change.
120 <a id="l111" href="#l111">111</a> 
121 <a id="l112" href="#l112">112</a> ## Extra-dim light
122 <a id="l113" href="#l113">113</a> 
123 <a id="l114" href="#l114">114</a> On the Viwoods reader the frontlight is a backlight LED whose driver accepts
124 <a id="l115" href="#l115">115</a> 1-255 (2047 real steps), but the framework snaps anything under 5 to zero, by
125 <a id="l116" href="#l116">116</a> every official route including `cmd display set-brightness`. Writing
126 <a id="l117" href="#l117">117</a> `/sys/class/leds/lcd-backlight/brightness` directly gets under the floor and
127 <a id="l118" href="#l118">118</a> sticks until the system slider is moved. The node belongs to `system`, so it
128 <a id="l119" href="#l119">119</a> needs Shizuku running as root or a shell that may `su` (userdebug firmware).
129 <a id="l120" href="#l120">120</a> 
130 <a id="l121" href="#l121">121</a> ## Menus, and export and import
131 <a id="l122" href="#l122">122</a> 
132 <a id="l123" href="#l123">123</a> `menu/`. The action *Menu of actions* binds a gesture to a menu with any number
133 <a id="l124" href="#l124">124</a> of actions. The menu is stored in the payload of its own binding, as a JSON
134 <a id="l125" href="#l125">125</a> array of action specs. There is no second store. A menu cannot hold a menu.
135 <a id="l126" href="#l126">126</a> `MenuActivity` closes before it runs the chosen action, because Back, a swipe
136 <a id="l127" href="#l127">127</a> or voice typing act on the app in front.
137 <a id="l128" href="#l128">128</a> 
138 <a id="l129" href="#l129">129</a> `store/SettingsFile.kt` turns the settings into one JSON document and back. It
139 <a id="l130" href="#l130">130</a> has no Android types, so tests run it with no device. `SettingsFile.ALLOWED` is
140 <a id="l131" href="#l131">131</a> the only list of what may pass, in both directions. The licence, the firmware
141 <a id="l132" href="#l132">132</a> values that `PowerControl` saved, and facts about one device are not in it.

151 <a id="l142" href="#l142">142</a> ## Voice typing
152 <a id="l143" href="#l143">143</a> 
153 <a id="l144" href="#l144">144</a> `voice/`. The action *Typing &gt; Voice typing* turns a key into a dictation key.
154 <a id="l145" href="#l145">145</a> The app has no speech engine and no network access. It calls the Android
155 <a id="l146" href="#l146">146</a> `SpeechRecognizer` interface, so a speech recognition app on the device does
156 <a id="l147" href="#l147">147</a> the listening: the system one, an offline Whisper app, or any other app that
157 <a id="l148" href="#l148">148</a> offers a `RecognitionService`. `TextInsert` then puts the words into the field
158 <a id="l149" href="#l149">149</a> that has input focus, through the accessibility service: `ACTION_SET_TEXT` at
159 <a id="l150" href="#l150">150</a> the selection, with a clipboard paste as the fallback. It never writes into a
160 <a id="l151" href="#l151">151</a> password field.
161 <a id="l152" href="#l152">152</a> 
162 <a id="l153" href="#l153">153</a> The app does not bundle a Whisper model. A multilingual model is 140 MB or
163 <a id="l154" href="#l154">154</a> more, and with no `INTERNET` permission the app could not download one. The
164 <a id="l155" href="#l155">155</a> F-Droid app Whisper (`org.woheller69.whisper`) already does this work and
165 <a id="l156" href="#l156">156</a> offers a `RecognitionService`, so voice typing uses it. `Dictation.pick` chooses
166 <a id="l157" href="#l157">157</a> an on-device speech app before one that may use a server. With no language tag
167 <a id="l158" href="#l158">158</a> set, the speech app detects the language.
168 <a id="l159" href="#l159">159</a> 
169 <a id="l160" href="#l160">160</a> Two facts cost time:
170 <a id="l161" href="#l161">161</a> 
171 <a id="l162" href="#l162">162</a> - Android gives the microphone to the app in front only, and an accessibility
172 <a id="l163" href="#l163">163</a>   service does not count (`RECORD_AUDIO` app-op mode is `foreground`). The
173 <a id="l164" href="#l164">164</a>   listening therefore runs in `DictationActivity`, which is see-through and
174 <a id="l165" href="#l165">165</a>   cannot take focus or touches.
175 <a id="l166" href="#l166">166</a> - The speech recognition app needs its own microphone permission too. If it has
176 <a id="l167" href="#l167">167</a>   none, the framework answers `ERROR_INSUFFICIENT_PERMISSIONS` and blames the
177 <a id="l168" href="#l168">168</a>   caller.
178 <a id="l169" href="#l169">169</a> 
179 <a id="l170" href="#l170">170</a> The Viwoods voice prompt is not reusable. It uploads audio to the Viwoods cloud
180 <a id="l171" href="#l171">171</a> (`/api/v1/openAi/speechToTextGemini`) and offers no interface to other apps.
181 <a id="l172" href="#l172">172</a> 
182 <a id="l173" href="#l173">173</a> Debug builds carry `FakeRecognitionService`, which hears a fixed sentence, so
183 <a id="l174" href="#l174">174</a> the whole chain can be tested on a bench with no voice.
184 <a id="l175" href="#l175">175</a> 
185 <a id="l176" href="#l176">176</a> ## Home, recent apps, speech: apps of other makers
186 <a id="l177" href="#l177">177</a> 
187 <a id="l178" href="#l178">178</a> Rebind has no recent-apps screen of its own. That screen is a program of its
188 <a id="l179" href="#l179">179</a> own, open source: [Ink Recents](https://github.com/equwal/ink-recents). The
189 <a id="l180" href="#l180">180</a> Recent apps action opens it (`dev.equwal.inkrecents.OPEN`). Where it is not
190 <a id="l181" href="#l181">181</a> installed, the action opens the screen that offers it. `home/RecentsActivity`
191 <a id="l182" href="#l182">182</a> is only that stand-in, and keeps the class name that old bindings hold.
192 <a id="l183" href="#l183">183</a> 
193 <a id="l184" href="#l184">184</a> Rebind has no home screen of its own. The `full` build carries the release
194 <a id="l185" href="#l185">185</a> APKs of other makers, not changed, in `app/src/full/assets/bundled/`, and
195 <a id="l186" href="#l186">186</a> installs them with `REQUEST_INSTALL_PACKAGES`: inkOS and ThinkLauncher (home
196 <a id="l187" href="#l187">187</a> screens for e-ink, GPL-3.0), Ink Recents (GPL-3.0) and Whisper (speech to
197 <a id="l188" href="#l188">188</a> text, MIT).
198 <a id="l189" href="#l189">189</a> `NOTICE.txt` in that folder names each maker, licence, source and SHA-256.
199 <a id="l190" href="#l190">190</a> Android asks the user before each install. The `play` build carries nothing
200 <a id="l191" href="#l191">191</a> and has no install permission. It opens the page of the maker.

202 <a id="l193" href="#l193">193</a> ## Why it is shaped like this
203 <a id="l194" href="#l194">194</a> 
204 <a id="l195" href="#l195">195</a> Android does not offer one way to intercept hardware keys. It offers several
205 <a id="l196" href="#l196">196</a> partial ones, each with different reach, and the power button has none at all.
206 <a id="l197" href="#l197">197</a> So the app is organised around **capture channels**: independent routes by which
207 <a id="l198" href="#l198">198</a> a key press can be made to arrive at this app. You tick the ones you want.
208 <a id="l199" href="#l199">199</a> 
209 <a id="l200" href="#l200">200</a> | Channel | Captures | How | Needs |
210 <a id="l201" href="#l201">201</a> |---|---|---|---|
211 <a id="l202" href="#l202">202</a> | **Accessibility key filter** | AI key, Volume up, Volume down | `AccessibilityService.onKeyEvent` with `flagRequestFilterKeyEvents` | Service enabled in Settings |
212 <a id="l203" href="#l203">203</a> | **Digital assistant** | Power — press and hold | Holds `ROLE_ASSISTANT`; the firmware fires `ACTION_ASSIST` at the role holder | Role granted; firmware long-press set to Assistant |
213 <a id="l204" href="#l204">204</a> | **Camera app** | Power — double press | Becomes the default camera, so the double-press camera gesture lands here | Set as default camera app |
214 <a id="l205" href="#l205">205</a> | **Wallet app** | Wallet tile, lock-screen wallet button; double-press Power on firmware that targets the wallet | Holds `ROLE_WALLET` and serves an (empty) `QuickAccessWalletService` | Role granted |
215 <a id="l206" href="#l206">206</a> 
216 <a id="l207" href="#l207">207</a> ### What was measured, and how
217 <a id="l208" href="#l208">208</a> 
218 <a id="l209" href="#l209">209</a> `adb shell input keyevent` is useless for this: injected events skip the input
219 <a id="l210" href="#l210">210</a> filter stage, so they say nothing about what a real press does. Everything
220 <a id="l211" href="#l211">211</a> below was measured as root with `sendevent` on the kernel input nodes, which
221 <a id="l212" href="#l212">212</a> enters the pipeline exactly where the hardware does.
222 <a id="l213" href="#l213">213</a> 
223 <a id="l214" href="#l214">214</a> | Press | Node | Result |
224 <a id="l215" href="#l215">215</a> |---|---|---|
225 <a id="l216" href="#l216">216</a> | AI key (`KEY_F1`), stock or unset hook | `event5` &quot;AI KEY&quot; | Reaches the filter, **and the firmware opens its AI screen anyway**, consumed or not |
226 <a id="l217" href="#l217">217</a> | AI key, hook set to anything else | `event5` | Firmware launches that component; the filter never sees the key |
227 <a id="l218" href="#l218">218</a> | Power held, then another key | `event1` + key | The second key reaches the filter; no screenshot or power-menu chord fires |
228 <a id="l219" href="#l219">219</a> | Volume up / down | `event1` / `event2` | Reaches the filter **only while its firmware hook is unset** |
229 <a id="l220" href="#l220">220</a> | Power, held 700 ms | `event1` | Firmware fires `ACTION_ASSIST` at the assistant role holder — us |
230 <a id="l221" href="#l221">221</a> | Power, twice within 300 ms | `event1` | `GestureLauncherService` fires `STILL_IMAGE_CAMERA`; never the wallet |
231 <a id="l222" href="#l222">222</a> 
232 <a id="l223" href="#l223">223</a> ### Firmware hooks can hide a key
233 <a id="l224" href="#l224">224</a> 
234 <a id="l225" href="#l225">225</a> The firmware has its own per-key settings in `Settings.System`:
235 <a id="l226" href="#l226">226</a> `CustomAiKey`, `CustomVolumeUpKey`, `CustomVolumeDownKey`. While a volume hook
236 <a id="l227" href="#l227">227</a> holds **any** value — even its default token, `volume_up` — the firmware deals
237 <a id="l228" href="#l228">228</a> with that key before the filter stage and no app ever sees it. Unset, the key
238 <a id="l229" href="#l229">229</a> arrives normally. The device&#x27;s own key-settings screen sets them.
239 <a id="l230" href="#l230">230</a> 
240 <a id="l231" href="#l231">231</a> The AI key is worse. With the stock hook the filter does see it, but the
241 <a id="l232" href="#l232">232</a> firmware opens its AI screen on every press regardless, so a binding fires on
242 <a id="l233" href="#l233">233</a> top of that screen. The only clean route is to point the hook at this app&#x27;s
243 <a id="l234" href="#l234">234</a> `AiKeyActivity`: every press then arrives as a launch, which is enough to count
244 <a id="l235" href="#l235">235</a> taps (but not to see a release, so no hold and no volume combinations):
245 <a id="l236" href="#l236">236</a> 
246 <a id="l237" href="#l237">237</a> ```bash
247 <a id="l238" href="#l238">238</a> tools/ai-key hook      # or: unhook, status
248 <a id="l239" href="#l239">239</a> ```
249 <a id="l240" href="#l240">240</a> 
250 <a id="l241" href="#l241">241</a> An ordinary app cannot write these. `SettingsProvider` rejects any
251 <a id="l242" href="#l242">242</a> `Settings.System` name outside its public list unless the caller is a
252 <a id="l243" href="#l243">243</a> privileged system app, with or without `WRITE_SECURE_SETTINGS`:
253 <a id="l244" href="#l244">244</a> *&quot;You cannot keep your settings in the secure settings.&quot;* So
254 <a id="l245" href="#l245">245</a> *Advanced → Firmware key hooks* is read-only: it shows each hook, says when one
255 <a id="l246" href="#l246">246</a> is hiding a key, and gives the fix:
256 <a id="l247" href="#l247">247</a> 
257 <a id="l248" href="#l248">248</a> ```bash
258 <a id="l249" href="#l249">249</a> adb shell settings delete system CustomVolumeUpKey
259 <a id="l250" href="#l250">250</a> adb shell settings delete system CustomVolumeDownKey
260 <a id="l251" href="#l251">251</a> ```
261 <a id="l252" href="#l252">252</a> 
262 <a id="l253" href="#l253">253</a> ### The power button is not like the others
263 <a id="l254" href="#l254">254</a> 
264 <a id="l255" href="#l255">255</a> `PhoneWindowManager.interceptKeyBeforeQueueing()` consumes `KEYCODE_POWER`
265 <a id="l256" href="#l256">256</a> before the input dispatcher runs, so **no** accessibility service, on any
266 <a id="l257" href="#l257">257</a> Android version, can see it. That leaves exactly three reachable slots:
267 <a id="l258" href="#l258">258</a> 
268 <a id="l259" href="#l259">259</a> - **Short press** — firmware only. The app rewrites
269 <a id="l260" href="#l260">260</a>   `Settings.Global.power_button_short_press`, so it can become Home, or nothing,
270 <a id="l261" href="#l261">261</a>   instead of sleep. No app code runs.
271 <a id="l262" href="#l262">262</a> - **Double press** — arrives as a camera launch. With more than one camera app
272 <a id="l263" href="#l263">263</a>   installed Android shows a chooser the first time; pick AssistKey and
273 <a id="l264" href="#l264">264</a>   *Always*.
274 <a id="l265" href="#l265">265</a> - **Press and hold** — arrives as an assistant request.
275 <a id="l266" href="#l266">266</a> 
276 <a id="l267" href="#l267">267</a> That is the position **without shell access**. With it, none of this section
277 <a id="l268" href="#l268">268</a> applies - see *Shell access*. Without it there is no multi-tap beyond two, and
278 <a id="l269" href="#l269">269</a> Power cannot take part in an ordinary combination, but there is one way in: a held Power announces itself, because the firmware
279 <a id="l270" href="#l270">270</a> fires the assistant at us, and a key pressed while it is still down reaches the
280 <a id="l271" href="#l271">271</a> filter. So **hold Power, then press** the AI key, Volume up or Volume down is
281 <a id="l272" href="#l272">272</a> three real combinations. While any is bound, the plain hold action waits one
282 <a id="l273" href="#l273">273</a> second to see whether a key follows.
283 <a id="l274" href="#l274">274</a> `Power + Volume up` is reserved by the firmware for the power menu, which the
284 <a id="l275" href="#l275">275</a> app deliberately leaves alone as an escape hatch.
285 <a id="l276" href="#l276">276</a> 
286 <a id="l277" href="#l277">277</a> ### Everything else
287 <a id="l278" href="#l278">278</a> 
288 <a id="l279" href="#l279">279</a> The AI key and both volume keys go through the accessibility filter, which gives
289 <a id="l280" href="#l280">280</a> the full vocabulary: 1–5 taps, press-and-hold, and any combination of those
290 <a id="l281" href="#l281">281</a> three keys, each bindable separately.
291 <a id="l282" href="#l282">282</a> 
292 <a id="l283" href="#l283">283</a> The gesture engine (`engine/GestureEngine.kt`) is deliberately free of Android
293 <a id="l284" href="#l284">284</a> types so the state machine is unit-testable on the JVM. Its one rule that
294 <a id="l285" href="#l285">285</a> matters for feel: *a key with no bindings is never consumed, and a key whose
295 <a id="l286" href="#l286">286</a> highest bound tap count is 1 fires on key-up without waiting out the multi-tap
296 <a id="l287" href="#l287">287</a> window.* You only pay multi-tap latency on keys where you actually asked for a
297 <a id="l288" href="#l288">288</a> double tap.
298 <a id="l289" href="#l289">289</a> 
299 <a id="l290" href="#l290">290</a> ## Navigation
300 <a id="l291" href="#l291">291</a> 
301 <a id="l292" href="#l292">292</a> *Navigation* on the main screen mixes three ways of getting around: the
302 <a id="l293" href="#l293">293</a> three-button bar, swipe gestures, and Power key combinations (defaults: Power
303 <a id="l294" href="#l294">294</a> then Volume up = Back, the AI key = Home, Volume down = Recents). Five named
304 <a id="l295" href="#l295">295</a> setups, or tick any mix.
305 <a id="l296" href="#l296">296</a> 
306 <a id="l297" href="#l297">297</a> The combinations are the app&#x27;s own. The bar and the gestures are the system&#x27;s,
307 <a id="l298" href="#l298">298</a> and Android lets no app switch them, so the screen shows the current state and
308 <a id="l299" href="#l299">299</a> the commands, and `tools/nav-mode` runs them:
309 <a id="l300" href="#l300">300</a> 
310 <a id="l301" href="#l301">301</a> ```bash
311 <a id="l302" href="#l302">302</a> tools/nav-mode buttons   nogestures    # bar only, no gestures at all
312 <a id="l303" href="#l303">303</a> tools/nav-mode nobuttons gestures      # gestures only
313 <a id="l304" href="#l304">304</a> tools/nav-mode nobuttons nogestures    # neither: Power combinations only
314 <a id="l305" href="#l305">305</a> tools/nav-mode status
315 <a id="l306" href="#l306">306</a> ```
316 <a id="l307" href="#l307">307</a> 
317 <a id="l308" href="#l308">308</a> | Piece | Switch |
318 <a id="l309" href="#l309">309</a> |---|---|
319 <a id="l310" href="#l310">310</a> | Button bar | overlay `com.android.internal.systemui.navbar.threebutton` / `.gestural` (gestural removes the bar outright on this firmware) |
320 <a id="l311" href="#l311">311</a> | Swipe up for Home (Viwoods&#x27; own, both modes) | `Settings.System disable_gesture_bottom` |
321 <a id="l312" href="#l312">312</a> | Edge swipe for Back (gestural mode only) | `Settings.Secure back_gesture_inset_scale_left/right` = 0 |
322 <a id="l313" href="#l313">313</a> 
323 <a id="l314" href="#l314">314</a> Order matters: changing the overlay makes SystemUI forget
324 <a id="l315" href="#l315">315</a> `disable_gesture_bottom`, so the overlay goes first.
325 <a id="l316" href="#l316">316</a> 
326 <a id="l317" href="#l317">317</a> Back, Home and Recents on a Power combination keep working when the app is
327 <a id="l318" href="#l318">318</a> locked. A reader with no bar and no gestures is navigated entirely by them, and
328 <a id="l319" href="#l319">319</a> an expired trial must not turn it into a brick.
329 <a id="l320" href="#l320">320</a>

345 <a id="l336" href="#l336">336</a> ## Installing
346 <a id="l337" href="#l337">337</a> 
347 <a id="l338" href="#l338">338</a> From Google Play, or sideload `AssistKey-&lt;version&gt;.apk` from the GitHub
348 <a id="l339" href="#l339">339</a> release. Both are the same build with the same signature.
349 <a id="l340" href="#l340">340</a> 
350 <a id="l341" href="#l341">341</a> On a Viwoods reader Google Play is switched off out of the box. The app works
351 <a id="l342" href="#l342">342</a> without it; buying a licence does not.
352 <a id="l343" href="#l343">343</a> 
353 <a id="l344" href="#l344">344</a> ### The accessibility switch will not stay on until you do this
354 <a id="l345" href="#l345">345</a> 
355 <a id="l346" href="#l346">346</a> Android blocks **restricted settings** for anything installed outside an app
356 <a id="l347" href="#l347">347</a> store, and accessibility is one of them. The symptom is silent and confusing:
357 <a id="l348" href="#l348">348</a> the switch appears to turn on, then reverts a moment later with no message.
358 <a id="l349" href="#l349">349</a> 
359 <a id="l350" href="#l350">350</a> *App info → three-dot menu → Allow restricted settings*, then enable the
360 <a id="l351" href="#l351">351</a> service. The app links straight to App info from the accessibility channel.
361 <a id="l352" href="#l352">352</a> 
362 <a id="l353" href="#l353">353</a> Over adb the equivalent is:
363 <a id="l354" href="#l354">354</a> 
364 <a id="l355" href="#l355">355</a> ```bash
365 <a id="l356" href="#l356">356</a> adb shell appops set dev.equwal.assistkey ACCESS_RESTRICTED_SETTINGS allow
366 <a id="l357" href="#l357">357</a> ```
367 <a id="l358" href="#l358">358</a> 
368 <a id="l359" href="#l359">359</a> Note that `adb shell am force-stop` on this app disables its accessibility
369 <a id="l360" href="#l360">360</a> service again, so re-enable it after any force-stop or reinstall.
370 <a id="l361" href="#l361">361</a> 
371 <a id="l362" href="#l362">362</a> ### Optional: the firmware power switches
372 <a id="l363" href="#l363">363</a> 
373 <a id="l364" href="#l364">364</a> ```bash
374 <a id="l365" href="#l365">365</a> adb shell pm grant dev.equwal.assistkey android.permission.WRITE_SECURE_SETTINGS
375 <a id="l366" href="#l366">366</a> ```
376 <a id="l367" href="#l367">367</a> 
377 <a id="l368" href="#l368">368</a> Without that grant everything still works except the firmware-level power
378 <a id="l369" href="#l369">369</a> switches (short press, hold duration, the double-press gesture toggles). The app
379 <a id="l370" href="#l370">370</a> detects the refusal and prints the exact `adb` command instead of failing
380 <a id="l371" href="#l371">371</a> silently.
381 <a id="l372" href="#l372">372</a> 
382 <a id="l373" href="#l373">373</a> Note that this permission only unlocks *writes*. Since Android 12 those keys
383 <a id="l374" href="#l374">374</a> cannot be **read** by a non-system app at all — `Settings.Global.getInt` throws
384 <a id="l375" href="#l375">375</a> `SecurityException` — so the app shows their current values as &quot;unknown&quot;. That
385 <a id="l376" href="#l376">376</a> is a platform restriction, not a bug.
386 <a id="l377" href="#l377">377</a> 
387 <a id="l378" href="#l378">378</a> ### Key tester
388 <a id="l379" href="#l379">379</a> 
389 <a id="l380" href="#l380">380</a> *Advanced → Key tester* lists every key event that reaches the filter. It is the
390 <a id="l381" href="#l381">381</a> only reliable way to find out what a given device allows, because a key consumed
391 <a id="l382" href="#l382">382</a> upstream by the window manager never reaches any app and simply never appears.
392 <a id="l383" href="#l383">383</a> Note that events injected with `adb shell input keyevent` **bypass**
393 <a id="l384" href="#l384">384</a> accessibility input filters entirely, so only real presses tell you anything.
394 <a id="l385" href="#l385">385</a> 
395 <a id="l386" href="#l386">386</a> ## Licensing
396 <a id="l387" href="#l387">387</a> 
397 <a id="l388" href="#l388">388</a> Four tiers, tried in order (`license/License.kt`):
398 <a id="l389" href="#l389">389</a> 
399 <a id="l390" href="#l390">390</a> | Tier | When | Effect |
400 <a id="l391" href="#l391">391</a> |---|---|---|
401 <a id="l392" href="#l392">392</a> | Licensed | Play reports `assistkey_pro` or `assistkey_pro_tester` owned | Everything works; cached, so it survives being offline |
402 <a id="l393" href="#l393">393</a> | Beta | The beta is open | Everything works, free; the install marks itself as a tester |
403 <a id="l394" href="#l394">394</a> | Trial | Beta closed, under 7 days since first launch | Everything works |
404 <a id="l395" href="#l395">395</a> | Locked | Otherwise | Key filter and entry points go inert; bindings are kept |
405 <a id="l396" href="#l396">396</a> 
406 <a id="l397" href="#l397">397</a> &quot;Is the beta open&quot; is answered by Google Play, not by a server. A third
407 <a id="l398" href="#l398">398</a> product, `assistkey_beta_open`, is never sold and exists only as a flag:
408 <a id="l399" href="#l399">399</a> deactivate it in Play Console and the beta ends everywhere. Only &quot;paid product
409 <a id="l400" href="#l400">400</a> visible **and** flag missing&quot;, in one response, reads as closed — so a failed
410 <a id="l401" href="#l401">401</a> or empty answer can never lock anyone out. Installs that cannot reach Play fall
411 <a id="l402" href="#l402">402</a> back to `assistkey.betaExpires` in `gradle.properties`.
412 <a id="l403" href="#l403">403</a> 
413 <a id="l404" href="#l404">404</a> Testers are then offered `assistkey_pro_tester`, the same licence for less. A
414 <a id="l405" href="#l405">405</a> tester on a new device types the tester code instead; only its SHA-256 ships.
415 <a id="l406" href="#l406">406</a> 
416 <a id="l407" href="#l407">407</a> The billing library&#x27;s telemetry runtime (`datatransport`) is excluded from the
417 <a id="l408" href="#l408">408</a> build, because it would merge `INTERNET` into the manifest. The library wraps
418 <a id="l409" href="#l409">409</a> that runtime&#x27;s start-up in a catch-all and logs *&quot;Skipping logging since
419 <a id="l410" href="#l410">410</a> initialization failed&quot;*; that was confirmed in bytecode and on the device.
420 <a id="l411" href="#l411">411</a> **Re-check it before bumping the billing version.**

422 <a id="l413" href="#l413">413</a> ## Building
423 <a id="l414" href="#l414">414</a> 
424 <a id="l415" href="#l415">415</a> ```bash
425 <a id="l416" href="#l416">416</a> ./gradlew assembleFullRelease assemblePlayRelease bundlePlayRelease
426 <a id="l417" href="#l417">417</a> ```
427 <a id="l418" href="#l418">418</a> 
428 <a id="l419" href="#l419">419</a> `bundlePlayRelease` makes the `.aab` for Play. `assembleFullRelease` makes the
429 <a id="l420" href="#l420">420</a> APK with shell access for direct install. `assemblePlayRelease` makes the store
430 <a id="l421" href="#l421">421</a> build as an APK, for testing it on a device. The version comes from `gradle.properties`; `versionCode` must rise with
431 <a id="l422" href="#l422">422</a> every upload.
432 <a id="l423" href="#l423">423</a> 
433 <a id="l424" href="#l424">424</a> Release signing is read from `keystore.properties` at the repo root, which is
434 <a id="l425" href="#l425">425</a> not committed:
435 <a id="l426" href="#l426">426</a> 
436 <a id="l427" href="#l427">427</a> ```properties
437 <a id="l428" href="#l428">428</a> storeFile=assistkey-release.jks
438 <a id="l429" href="#l429">429</a> storePassword=…
439 <a id="l430" href="#l430">430</a> keyAlias=assistkey
440 <a id="l431" href="#l431">431</a> keyPassword=…
441 <a id="l432" href="#l432">432</a> testerCode=…
442 <a id="l433" href="#l433">433</a> ```
443 <a id="l434" href="#l434">434</a> 
444 <a id="l435" href="#l435">435</a> Without it the release build still runs and produces an unsigned APK, so a fresh
445 <a id="l436" href="#l436">436</a> clone is never broken — it just cannot ship. **Back up the keystore**: losing it
446 <a id="l437" href="#l437">437</a> means shipped installs can never be upgraded.

448 <a id="l439" href="#l439">439</a> ### Windows note
449 <a id="l440" href="#l440">440</a> 
450 <a id="l441" href="#l441">441</a> If Gradle dies with `Unable to establish loopback connection`, `java.io.tmpdir`
451 <a id="l442" href="#l442">442</a> is resolving through an 8.3 short path (`C:\Users\ADMINI~1\…`), which breaks the
452 <a id="l443" href="#l443">443</a> JDK&#x27;s AF_UNIX-backed `Selector.open()`. Point `TMP` and `TEMP` at a short path
453 <a id="l444" href="#l444">444</a> such as `C:\tmp` and it goes away.
